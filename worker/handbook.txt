1. Project Overview
1.1 Problem Statement
Enterprise knowledge is siloed across PDFs, Word documents, Notion pages, Confluence wikis, and shared drives. Employees waste hours searching for answers that already exist internally. Traditional search (keyword-based) fails when documents are large, terminology varies, or context matters.
Existing SaaS solutions like Guru, Notion AI, and Confluence AI are generic, expensive at scale, and don't offer true multi-tenant customization or white-labeling for B2B resale.
1.2 Vision
Build a production-grade, multi-tenant SaaS platform that transforms any company's document library into a conversational AI knowledge base — enabling employees to ask natural-language questions and receive precise, sourced answers drawn from internal documents only.
1.3 Key Use Cases
HR departments answering employee policy questions from the employee handbook
Legal teams querying contracts and compliance documentation
Engineering teams searching internal architecture docs, runbooks, and SOPs
Sales teams querying product specs, pricing decks, and case studies
Support teams answering customer queries from knowledge bases
1.4 Multi-Tenant Considerations
Every tenant (company) must be treated as a completely isolated data silo:
Documents, users, queries, and embeddings are never shared across tenants
Each tenant gets scoped vector DB namespace or collection isolation
RBAC (Role-Based Access Control) is enforced per tenant
Billing, quotas, and rate limits are enforced per tenant
Tenant admins can manage their own users and documents
2. System Architecture
2.1 High-Level Architecture
The system is decomposed into five major layers: Client, API Gateway, Core Services, AI/ML Layer, and Infrastructure. Each layer is independently deployable and scalable.
DESIGN PRINCIPLE
Each service owns its own data store and communicates via REST or async queues. No direct DB cross-talk between services.

2.3 End-to-End Data Flow
Document Ingestion Flow
User uploads PDF via frontend
Backend stores file to S3, creates document record in PostgreSQL with status: pending
Backend enqueues job to BullMQ: { documentId, companyId, s3Key }
Worker picks up job, downloads file from S3
Worker extracts text using pdf-parse / mammoth
Worker splits text into chunks (1000 chars, 200 overlap)
Worker calls AI service POST /embed for each chunk
AI service generates embedding via OpenAI text-embedding-3-small
AI service stores vector in Chroma with metadata: { chunkId, documentId, companyId, chunkText }
Worker updates document status to indexed
Query / RAG Flow
User types question in chat interface
Frontend sends POST /chat/query with { sessionId, query }
Backend extracts companyId from JWT, calls AI service
AI service embeds the query
AI service performs vector similarity search in tenant namespace, retrieves top-K chunks
AI service constructs prompt: system context + retrieved chunks + user question
AI service calls OpenAI GPT-4o, streams response
Backend streams response back to frontend via SSE
Backend logs query + response to queries table for analytics

5. AI Architecture — RAG Pipeline
5.1 RAG Pipeline Design
CORE PRINCIPLE
The model never hallucinates facts it doesn't have — it only answers from retrieved company documents. If no relevant chunks are found, the system responds: 'I could not find relevant information in your knowledge base.'

5.2 Chunking Strategy
Primary: RecursiveCharacterTextSplitter — splits on paragraphs → sentences → words
Chunk size: 1000 characters (~250 tokens) — fits comfortably in context with 5 chunks
Overlap: 200 characters — prevents losing context across chunk boundaries
Rejected: fixed token chunking — character-based is simpler and nearly as effective
Phase 2: Semantic chunking — split on semantic similarity rather than character count
5.3 Embedding Strategy
Model: text-embedding-3-small (1536 dimensions, $0.02/1M tokens)
Upgrade path: text-embedding-3-large (3072 dimensions) for higher accuracy
All chunks from the same document use the same model version — stored in metadata
Re-index all chunks when upgrading embedding model (worker job)

5.5 Context Window Management
GPT-4o context window: 128K tokens (as of 2024)
Each chunk: ~250 tokens. K=5 chunks = ~1,250 tokens of context.
Reserve 2,000 tokens for response generation
System prompt: ~200 tokens
Total consumption: ~3,500 tokens per query — well within limits
Token counting via tiktoken before sending to API — fail gracefully if over budget

7. Security Design
7.1 Tenant Isolation (Critical)
Layer 1 — JWT: company_id is encoded in every JWT. Verified on every request in auth middleware.
Layer 2 — Service layer: ALL database queries include WHERE company_id = req.tenantId
Layer 3 — DB RLS: PostgreSQL Row Level Security policies as final safety net
Layer 4 — Vector namespace: Chroma collection per company_id. Cross-namespace queries are impossible.
Layer 5 — S3 paths: Documents stored under s3://bucket/tenants/{companyId}/ — S3 bucket policies enforce isolation
CRITICAL
A data leak between tenants is a catastrophic security failure. All five layers must function together. Never skip a layer for performance.
7.2 Authentication Security
Access tokens: 15-minute expiry. Short-lived to limit exposure on token theft.
Refresh tokens: 7-day expiry, stored in httpOnly cookie (not localStorage).
Token rotation: issue new refresh token on every refresh. Previous token invalidated.
Refresh token family tracking: detect and block token reuse attacks.
Password hashing: bcrypt with 12 rounds minimum.
7.3 Document Security
Files are never served directly. Always via presigned S3 URLs with 1-hour expiry.
Virus scanning: ClamAV scan before document enters processing pipeline (Phase 2).
File type validation: server-side MIME type detection (not client-declared Content-Type).
Max file size enforced: 50MB default, configurable per tenant plan.
7.4 API Security
HTTPS only — HTTP redirects to HTTPS at NGINX layer.
CORS: whitelist only known frontend origins.
Helmet.js: sets security headers (CSP, HSTS, X-Frame-Options).
Input validation: Zod schemas on all request bodies. Reject unknown fields.
SQL injection: parameterized queries via Prisma ORM — never string interpolation.

13. Future Enhancements
13.1 AI Agents
Evolve the system from pure Q&A to autonomous task completion. An agent could: read documents → identify gaps → draft policy updates → route for approval. Built on LangGraph or CrewAI.
13.2 Team-Specific Knowledge Scopes
Within a company, teams (Engineering, Legal, HR) see only their department's documents. Implemented via document tags + RBAC policy + sub-namespace vector isolation.
13.3 Real-Time Collaboration
Multiple users in the same chat session, shared annotations on retrieved chunks, collaborative document review. Requires WebSocket infrastructure (Socket.io or Ably).
13.4 Fine-Tuned Models
For enterprise customers, fine-tune an open-source model (Mistral-7B, Llama-3) on their domain vocabulary. Reduces hallucination, improves terminology accuracy, and enables full on-premise deployment.
13.5 Knowledge Graph
Extract entity relationships from documents (people, projects, policies, dates) to build a company-specific knowledge graph. Enables relationship-aware queries: 'Who approved the Q3 procurement policy?'
